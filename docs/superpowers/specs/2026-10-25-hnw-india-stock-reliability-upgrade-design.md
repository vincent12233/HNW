# HNW 印度股票平台可靠性与体验升级设计

日期：2026-10-25  
状态：待用户审核，未授权实施

## 1. 设计意图

HNW 继续定位为面向印度市场的股票投资与交易 App。升级目标是同时吸收 Groww 的易用性、Zerodha Kite 的轻量与风险提示、Upstox 的交易连续性、Angel One 的运营完整性，在不改变现有交易规则、客户注册登录、员工登录、人工存款方式和角色权限边界的前提下，提高稳定性、并发能力、故障恢复能力和客户端/后台体验。

本设计把“完整升级”视为一个统一项目，但必须分阶段上线、逐步放量、可随时回滚。不得以一次性替换生产系统的方式交付。

## 2. 已确认边界

### 2.1 必须保持不变

- 客户继续使用印度手机号、密码和邀请码注册，不新增邮箱注册。
- 不擅自增加短信验证码或改变现有客户登录流程。
- 后台员工继续使用员工编号、密码和 Google Authenticator。
- 客户存款继续通过 Deposit / Contact Support 联系客服，由财务后台人工上分。
- 不改变现有股票交易规则、订单类型、撮合规则、资金冻结与结算语义。
- 五种后台角色继续服务端强制隔离，不能只依赖前端菜单。
- 当前 API 契约尽量向后兼容；不可避免的变化必须版本化。

### 2.2 最高优先级不可变业务红线

以下六条是本项目的回归判定标准，优先级高于架构、性能、视觉和代码整洁度。实现过程中只要任一行为被改变，即使其他指标提升，也判定该阶段失败并禁止发布。

| 受保护流程 | 必须保持的核心行为 | 允许优化 | 禁止改变 |
| --- | --- | --- | --- |
| 客户注册 | 印度手机号 + 密码 + 邀请码；沿用现有校验、接口和成功结果 | 布局、视觉、帮助文字、输入反馈、可访问性 | 增加邮箱、短信 OTP、新身份字段或改变邀请码逻辑 |
| 客户登录 | 注册手机号 + 密码；沿用现有令牌、会话和错误语义 | 页面 UI、文字、加载/失败反馈、设备适配 | 改变必填凭据、强制新增登录步骤或用新登录方式替代当前方式 |
| 忘记密码 | 继续由在线客服处理；客户连接客服后由客服签发恢复码，再使用现有恢复流程 | 页面说明、状态反馈、错误提示和客服入口体验 | 改成短信、邮箱、自助重置，或绕过客服签发恢复码 |
| 存款 | App 的 Deposit / Contact Support 继续进入在线客服；财务后台继续人工上分 | 引导文字、状态展示、客服衔接、后台操作效率 | App 内创建自动充值、支付网关、UPI 自动入金或链上入金 |
| 交易方式 | 保留现有 BUY/SELL、MARKET/LIMIT、DAY/IOC/FOK、数量/限价、冻结、撮合、撤单、结算和幂等语义 | 稳定性、错误反馈、确认信息、性能和可观测性 | 新增/删除订单类型，改变字段含义、撮合、资金冻结、成交或撤单规则 |
| 交易页面 | 保留现有入口、股票上下文、买卖方向、订单类型、有效期、数量、限价、确认与提交路径 | UI/UX、文字、信息层级、触控尺寸、加载/失败状态、无障碍 | 删除核心字段、预填会改变订单的值、跳过确认、自动提交或改变请求载荷 |
| 客户端信息边界 | 只显示客户完成证券业务所需的信息，以及经运营主体和合规人员批准的法定披露 | 用户友好说明、业务帮助、风险提示和安全 requestId | 暴露项目内部信息、源码/仓库、技术栈、接口/服务器地址、环境名、数据库字段、内部角色、供应商配置、密钥、调试堆栈、测试数据或内部业务编号 |

员工后台登录、首次 Google Authenticator 绑定、后续动态码登录和分级重置权限同样属于受保护安全契约，不因 UI/UX 升级而改变。

### 2.3 回归事实源

- 以实施开始时用户批准的 `main` 完整提交 SHA 作为唯一升级基线。
- 现有 characterization tests、HTTP 契约测试、数据库约束、Flutter 服务请求模型和用户已确认的业务规则共同组成回归事实源。
- 如代码、文档和测试互相冲突，先暂停该模块，由用户确认实际业务行为；不得擅自选择“看起来更合理”的版本。
- 开始升级前先为上述六条红线生成请求/响应快照、数据库前后状态、关键页面流程和自动化回归测试。
- 每个 PR 都必须运行红线回归套件；出现任何请求字段、状态转换、金额结果或页面核心流程差异时阻止合并。
- UI 文案允许调整，但涉及金额含义、订单状态、风险、确认结果和客服重置/存款步骤的文字必须保持事实准确。
- Flutter 客户端不得作为项目说明书或运维面板。项目版本 SHA、构建环境、健康检查、基础设施状态、后台权限结构和供应商诊断只进入受控后台/监控系统。
- 客户端错误只显示安全、可行动的提示和可供客服查询的 requestId；详细异常、SQL、内部路径、第三方响应和堆栈仅写入脱敏后的服务端日志。

### 2.4 明确不做

- 不加入加密货币、区块链、热钱包、冷钱包、NFT、DeFi 或链上充值提现。
- 不新增未经产品和合规单独批准的 F&O、杠杆、复制交易、自动策略、GTT、Basket 或 API 交易。
- 不为了“微服务化”大规模重写现有 NestJS 业务代码。
- 不把 Redis、Kafka 或客户端缓存作为余额、订单或成交的最终事实来源。
- 不伪造 NSE/BSE 实时行情、合规许可、交易所连接或供应商 SLA。
- 不在没有真实数据时展示模拟收益、伪造运营指标或虚假“实时”状态。

## 3. 方案选择

### 3.1 方案 A：只做 UI/UX 与单体性能优化

优点是改动少、风险低；缺点是不能系统性解决多实例一致性、行情故障、数据库高可用、异步任务和灾备问题。

### 3.2 方案 B：模块化单体 + 可靠事件架构（选定）

保留 NestJS API 和现有业务模块，增加网关、多实例部署、数据库高可用、Redis、事务 Outbox、事件总线、读模型和故障演练。关键交易与资金写入仍由 PostgreSQL 事务保护。

该方案能在不重写业务逻辑的情况下完成工业级加固，也是当前仓库结构和团队运维复杂度之间的最佳平衡。

### 3.3 方案 C：全面微服务重写

长期扩展空间最大，但会引入分布式事务、跨服务一致性和更高运维门槛。当前项目不采用；只有某一模块已通过监控证据证明无法独立扩展时，才允许从模块化单体中拆出。

## 4. 目标架构

```text
Flutter 客户 App               五角色 Next.js Admin
        │                              │
        └──────── HTTPS / WSS ─────────┘
                       │
             CDN / DDoS / WAF
                       │
          Load Balancer / API Gateway
        路由、限流、请求大小、超时、追踪
                       │
       ┌───────────────┴───────────────┐
       │       NestJS API 多实例        │
       │ Auth / KYC / Account / Orders │
       │ Funding / Admin / Market Data │
       └───────────────┬───────────────┘
                       │
       ┌───────────────┼────────────────┐
       │               │                │
 Redis HA/Cluster  PostgreSQL HA    Event Workers
 限流/短缓存       交易事实源         Outbox 消费
 会话撤销状态       审计/账本          通知/报表
       │               │                │
       │        Read Replica       Kafka 或兼容总线
       │        后台查询/报表       非关键异步事件
       │
 Market WebSocket Hub ─── TimescaleDB
 实时报价分发             Tick/K线/时序数据
```

### 4.1 网关与边缘层

- 生产入口统一经过 CDN、DDoS 防护和 WAF。
- 网关负责 TLS、HTTP/WSS 路由、请求体上限、连接上限、IP/设备/账户多维限流、超时和 request ID。
- 身份授权、金额权限和业务规则仍由 NestJS 服务端执行，网关不是权限最终边界。
- 管理后台与客户 API 使用独立域名和限流策略。
- 指标、健康检查和管理端点只允许私网访问。
- 网关配置必须版本化并经过 CI 校验；错误规则可独立回滚。

### 4.2 NestJS 模块化单体

- 保留现有 Auth、KYC、Account、Deposit、Withdrawal、Orders、Trading、Matching、Market Data、Admin 和 Audit 模块。
- 通过明确的模块接口减少跨模块直接数据库访问。
- 订单、资金、KYC、后台审批都保持现有 API 语义。
- API 实例无状态化；会话撤销、共享限流和短期协调放入 Redis，永久事实写入 PostgreSQL。
- 慢任务不得阻塞 HTTP 请求线程，改由可重试 Worker 执行。

### 4.3 Redis

- 用于共享限流、短时行情缓存、会话撤销状态、分布式短租约和热点读缓存。
- 不存放唯一余额、唯一订单或唯一成交记录。
- 关键安全接口保持 fail closed：Redis 不可用时不得绕过限流或会话撤销检查。
- 普通非关键缓存采用 fail open，但响应必须标识数据时间和可能过期状态。
- 所有缓存键包含版本、租户/角色范围和 TTL，禁止无限期键。

### 4.4 PostgreSQL

- PostgreSQL 是客户、账户、订单、成交、资金流水、审批和审计的最终事实源。
- 使用主库高可用、自动故障转移、PgBouncer 和只读副本。
- 交易写请求只进入主库；后台列表、报表和非实时统计可进入只读副本。
- 读副本响应必须容忍复制延迟；刚完成的资金/订单写入使用主库读回。
- 余额变化通过不可变流水和事务内汇总更新完成，禁止无审计的直接覆盖。
- 所有资金状态转换采用行锁/事务级 advisory lock、版本检查和唯一幂等键。

### 4.5 TimescaleDB

- 只保存 Tick、OHLCV、分钟线、日线和行情健康数据。
- 与交易资金库逻辑隔离，行情写入故障不得锁住下单或余额事务。
- K 线由确定性聚合任务生成，支持迟到 Tick 修正和聚合版本。
- 数据保留、压缩和降采样按周期配置；客户端永远获得数据时间戳和来源状态。

### 4.6 Outbox 与事件总线

- 业务事务在同一 PostgreSQL 事务内写入业务记录和 Outbox 记录。
- 独立 Worker 投递 Outbox；消费者必须幂等，允许消息至少一次投递。
- Kafka/兼容事件总线仅承载通知、报表、行情加工、审计复制和读模型更新。
- 资金扣减、冻结、结算成功不能仅由“消息已发送”决定。
- 事件包含 eventId、aggregateId、aggregateVersion、occurredAt、schemaVersion 和 correlationId。
- 事件 Schema 只能向后兼容演进，不允许消费者依赖未声明字段。

## 5. 订单、交易与资金可靠性

### 5.1 订单命令路径

```text
客户端生成 clientOrderId / Idempotency-Key
  → 网关基础校验与限流
  → API 身份、市场时段、标的、价格、数量与账户校验
  → 数据库事务锁定账户/订单范围
  → 冻结资金或持仓
  → 创建订单和账本流水
  → 写入 Outbox
  → 提交事务
  → 返回稳定 orderId 与当前状态
```

- 相同幂等键和相同请求体返回第一次结果。
- 相同幂等键和不同请求体必须冲突失败。
- 客户端超时后应查询订单状态，不盲目创建新订单。
- 任何错误响应都包含稳定业务错误码和 requestId。
- 不把“请求已接收”展示为“已成交”。

### 5.2 状态机

- 每种订单状态转换必须集中定义和测试。
- 并发撤单与成交使用版本号或行锁，最终只允许一个合法结果。
- 部分成交、完全成交、撤单、拒绝和市场收盘必须有确定性规则。
- 非法跳转必须拒绝并写安全审计。
- 后台不能直接修改订单状态，只能调用有权限和审计的业务命令。

### 5.3 账本与对账

- 每次冻结、释放、成交结算、人工入金、提现和后台调整都有唯一流水键。
- 账本采用追加模式，历史流水不原地改金额。
- 定时核对账户余额、冻结金额、订单、成交和资金流水。
- 差异进入隔离队列，禁止自动用“补一笔钱”方式静默修正。
- 对账异常在后台显示影响账户、金额、首次时间、最后时间和处理状态。

### 5.4 撮合边界

- 保留现有 Matching 业务语义，不在本轮替换为 LMAX/Go 撮合引擎。
- 先对现有撮合进行顺序一致性、确定性回放和并发压测。
- 只有实测证明 Node.js 撮合达到明确瓶颈，才允许设计独立撮合进程。
- 独立撮合候选必须先影子运行，对同一输入生成结果并与现有结果逐笔比对，不接触真实余额。

## 6. 行情与 K 线体验

- 行情消息带 instrument、exchange、sequence、sourceTimestamp、receivedAt 和 quality。
- WebSocket 客户端保存最后 sequence；发现缺口时请求快照并重建。
- 断线采用带随机抖动的指数退避，避免所有客户端同时重连。
- UI 明确区分 LIVE、DELAYED、STALE 和 UNAVAILABLE。
- 行情过期不能把旧价格显示为实时；余额和持仓请求失败不能显示为 0。
- 首页、Markets、股票详情和持仓复用统一行情状态模型。
- K 线周期与时区统一，印度市场日历和交易时段由服务端配置。
- 行情供应商切换必须经过适配器，避免供应商字段渗透到客户端。

## 7. 客户 App UI/UX

### 7.1 体验原则

- Groww：页面清晰、适合普通投资者、重点信息优先。
- Zerodha：轻量、快速、风险提示和订单透明。
- Upstox：行情、图表、下单、持仓和损益连续操作。
- Angel One：账户、运营、支持与交易能力组织完整。
- 只借鉴交互原则，不复制品牌、视觉资产或未经批准的产品能力。

### 7.2 信息架构

- Home：市场状态、主要指数、账户摘要、关注列表、市场动态和公告。
- Markets：NSE/BSE、涨跌榜、活跃榜、行业/类别筛选和搜索。
- Instrument：报价时间、行情质量、K 线、基础资料、市场深度和风险提示。
- Order Entry：买卖方向、订单类型、数量、价格、费用/资金影响、风险确认和最终提交。
- Orders：按状态组织，并显示每个状态的原因和时间线。
- Portfolio：持仓、平均成本、当前价值、当日损益、累计损益和可用资金。
- IPO：开放、即将开放、结束、申请记录和状态说明。
- Profile：KYC、银行账户、设备、通知偏好、安全、语言和支持。

### 7.3 所有页面必须覆盖的状态

- 首次加载、局部加载、刷新。
- 空数据。
- 权限拒绝。
- 网络离线。
- 超时。
- 服务端错误。
- 部分数据成功。
- 缓存数据/过期数据。
- 重试中。
- 重复提交被阻止。
- App 进入后台后恢复。
- 老请求晚于新请求返回。
- WebSocket 断线与重连。
- 低端 Android、窄屏、系统大字体和 reduced motion。

### 7.4 交易体验保护

- 提交按钮在请求期间锁定，但超时后提供“查询订单状态”，不简单再次提交。
- 下单确认页明确区分估算与最终结果。
- 拒单显示可行动原因，不展示内部堆栈或供应商错误。
- 关键金额统一使用 INR、₹ 和印度数字分组。
- 涨跌不只靠红绿颜色表达。
- 风险警告必须在提交前可见，不使用误导性的默认勾选。

### 7.5 网页版与 PWA

- 网页版复用现有 Flutter 客户端、API DTO 和受保护业务契约，不另建一套交易逻辑；手机浏览器、平板和桌面浏览器只改变响应式布局与输入方式。
- 桌面端使用有界内容宽度、可用侧栏/导航、键盘焦点、悬停状态和宽表格；窄屏保持现有移动信息架构。任何断点都不得隐藏订单字段、默认值、确认步骤或风险提示。
- PWA 使用正式名称、描述、主题色、图标、maskable 图标、启动范围和 standalone 展示；安装前后、浏览器标签与系统启动器保持一致品牌体验，但客户界面不显示仓库、技术栈、端点、环境或内部版本信息。
- Service Worker 只缓存带哈希的静态资源和最小 App Shell。登录、账户、资金、KYC、客服、订单、成交和行情 API 默认 network-only/no-store；不得把令牌、密码、PIN、个人资料或金融响应写入 Cache Storage。
- 离线时只显示明确的离线/过期状态和允许的非敏感壳内容；禁止离线排队、后台重放下单、撤单、存款、提现或资料提交。恢复联网后重新鉴权、刷新状态并查询未知结果。
- 新版本采用可见且可控的更新提示；不得在用户填写订单或提交写操作时强制刷新。静态资源与当前 HTML/Service Worker 版本不兼容时，进入安全恢复页而不是白屏。
- 支持深链和浏览器刷新，未知路径返回 App Shell 后由应用显示安全的未找到状态；退出登录、会话过期、多标签页并发和浏览器前进/后退必须有测试。
- Web 发布默认同源代理 API/WSS，启用 HTTPS、HSTS、CSP、frame-ancestors、Referrer-Policy、Permissions-Policy、正确 MIME 和压缩；构建产物不得包含秘密、私网地址或生产 source map。
- 验收 Chrome、Edge、Safari 和 Firefox 当前受支持版本；覆盖可安装性、Lighthouse PWA/无障碍基线、桌面/平板/手机截图、弱网、离线、更新、缓存清理和跨版本回滚。

### 7.6 企业级状态展示与反馈系统

- 不只修复 KYC 提交后的沙漏，必须盘点客户 App、Web/PWA 和后台所有加载、提交中、等待审核、处理中、成功、拒绝、失败、空数据、离线、过期和未知结果展示，统一升级。
- 建立共享状态场景组件：语义图标/插画区域、标题、简短说明、状态标签、更新时间、下一步、主次操作和可选进度时间线；页面不得继续散落巨大沙漏、孤立 Spinner、默认素材或风格不一致的结果页。
- KYC 提交后使用克制的“资料已收到”结果卡与 Submitted → Manual review → Result 时间线，明确当前状态和下一步；不得虚构审核完成时间，也不得改变人工审核流程。
- 订单、存款、提现、IPO、KYC、客服和账户安全必须区分“业务处理中”“网络请求中”“结果未知”“已失败”，禁止用同一个 Loading 图标掩盖不同含义。
- 参考 Groww、Zerodha、Upstox、Angel One 等成熟企业级 App 的信息层级、留白、状态语义和行动指引，但不复制其品牌、插画、商标或受保护资产。
- 动效应短、克制且可中断；支持 reduced motion。颜色不能成为唯一状态信号，图标、标题和文字必须共同表达含义。
- 空状态必须说明为什么为空以及用户能做什么；错误状态必须给出安全、可执行的恢复动作；成功状态不得夸大或提前宣告尚未完成的金融结果。
- 所有状态场景纳入英语/印地语、窄屏/横屏/平板/桌面、1.0/1.4 字号、明暗或高对比度模式的 Golden/截图验收，并检查语义标签与键盘焦点。

### 7.7 全页面覆盖，二级页面与覆盖层同等重要

- UI/UX 升级不得只覆盖 Home、Markets、Trade、Portfolio、Profile 等一级页面；所有可导航页面、二级详情、流程步骤、抽屉、底部面板、弹窗和结果页使用同一质量门槛。
- 建立受版本控制的客户界面清单，记录入口、页面层级、角色/前置条件、支持平台、关键状态、Golden/截图、负责人和验收结果；新增页面未登记时 CI 失败。
- 二级页面至少覆盖：股票搜索/详情、指数列表/详情、涨跌榜、市场新闻、通知、订单/成交/持仓详情、存款、提现、贷款、IPO、KYC 全步骤与自拍、银行资料、账户设置、安全、语言、外观、法律/内容、客服及其结果页面。
- 覆盖层同样纳入验收：订单确认、撤单确认、记录详情、持仓详情、新闻详情、公告详情、筛选器、设置抽屉、客服浮层和所有错误/成功对话框。
- 页面之间必须保持 AppBar、返回行为、标题层级、边距、滚动、键盘避让、SafeArea、加载/空/错状态和主次按钮一致；不得出现从精致主页面进入旧式二级页面的视觉断层。
- 每个页面验证正常、空、长文本、失败、离线、过期、大字体、窄屏、横屏和返回恢复；涉及写操作的页面还验证重复点击、超时、未知结果和输入保留。
- 二级页面优化仅改变视觉、信息层级、文案和反馈，不得改变注册、人工存款、KYC 审核、订单、结算或其他受保护业务契约。

## 8. 五角色后台 UI/UX

- 统一 AdminShell、导航、页面标题、筛选区、表格、分页、详情、审批和状态组件。
- 超级管理员关注治理、员工、权限、审计、系统健康和重大异常。
- 管理员关注客户、KYC、业务员和客户归属。
- 财务关注人工入金、提现、流水、差异和对账。
- 业务员只能查看自己的客户及允许的数据。
- 专用运营员只能查看固定邀请码范围内的客户。
- 所有写操作显示对象、当前值、新值、影响范围和原因输入。
- 高风险操作需要二次确认；必要时采用双人复核，但不得擅自改变现有审批规则。
- 大列表使用服务端分页、稳定排序和可取消请求。
- 导出通过后台任务生成，避免同步大查询拖垮 API。
- 实时仪表盘和业务报表分离；缓存/副本延迟必须标注更新时间。

### 8.1 完整管理系统与长期维护

- 后台按“治理、客户/KYC、资金、交易、内容、人员权限、审计、系统健康”组织，不按零散页面堆叠。
- 所有路由、菜单、角色权限、页面标题和面包屑来自集中注册表，避免各页面自行判断角色。
- 统一数据页面契约：服务端分页、筛选、排序、更新时间、空/错/拒绝/过期状态、详情和导出。
- 统一写操作契约：权限校验、幂等键、当前值/新值、影响范围、原因、确认、结果和审计。
- 建立后台系统健康页，只显示经过脱敏的 API、数据库、Redis、行情、Worker、Outbox、对账和版本健康摘要；不向普通客户 App 暴露。
- 建立配置治理：配置项有类型、默认值、环境来源、是否敏感、修改权限、审计和回滚；秘密值永不回显。
- 现有大页面按业务域拆成 focused components/hooks/services，禁止复制五套角色页面。
- 共享组件必须有契约测试和视觉测试；页面不得自行实现重复的金额、状态、权限和错误格式。
- 每个后台模块必须有维护说明：职责、路由、API、权限、数据来源、告警、常见故障和回滚方式。
- 新后台功能先扩展共享契约，再接入页面，避免形成新的孤立实现。

### 8.2 部署服务器便利性与运维管理

- 提供统一、可重复执行的部署入口，覆盖环境预检、镜像构建、配置校验、数据库迁移兼容检查、灰度发布、健康验证和代码回滚；禁止依赖人工复制文件或服务器内临时修改。
- 后台提供只读“部署与运行状态”视图：当前版本 SHA、构建时间、实例健康、迁移版本、Worker/队列状态、最近发布结果和回滚就绪状态。不得展示秘密值、主机凭据、数据库连接串或可执行终端。
- 生产发布只能从受保护的 CI/CD 环境触发，使用最小权限部署身份、审批门、并发锁和完整审计；后台业务角色不能直接执行服务器命令。
- 服务器配置采用版本化声明和环境模板，敏感值由 Secrets Manager/KMS/Vault 类服务注入；启动前验证必需变量、证书、磁盘、时钟、依赖版本和备份状态。
- 数据库迁移使用 expand/migrate/contract；发布前兼容检查，发布后 smoke test。失败时自动停止放量，并只回滚代码和流量，不回滚已提交的资金事实。
- 提供统一运维命令和文档，用于状态查看、日志关联、备份校验、维护模式、扩缩容、证书检查和安全回滚；危险动作必须二次确认、限定环境并写入审计。
- 每次发布生成可追溯清单：提交 SHA、镜像摘要、配置版本、迁移版本、审批人、验证证据、开始/完成时间和结果。
- 定期执行恢复演练、证书到期检查、磁盘容量告警、镜像与依赖更新、日志保留和权限复核，避免部署长期依赖单个人员经验。

### 8.3 后台模块与操作完整性

- 后台必须是可执行工作的管理系统，不是只读数据看板。每个模块建立“角色 × 数据范围 × 状态 × 可用操作”能力矩阵，并由服务端权限、前端入口和自动化测试共同约束。
- 模块完整性标准包括：列表、搜索/筛选、稳定排序、分页、详情、相关记录、状态历史、允许的操作、原因/备注、确认、执行结果、刷新恢复和审计；只在业务确实需要时提供导出。
- KYC 审核必须同时提供“通过”和“拒绝”。拒绝原因必填并向客户作为补件说明；两种决定都显示客户、当前状态、目标状态和影响，服务器确认前不得提前显示成功。
- KYC 审核应支持待审核/已通过/已拒绝筛选、安全资料预览、审核备注、审核人/时间（仅在服务端真实返回时）、失败重试和并发状态冲突提示。已完成审核不得被重复决定。
- 资金模块应在现有业务契约允许范围内完整呈现人工存款、提现、流水和对账的查看、通过、拒绝、原因、幂等结果和审计；不得添加绕过人工流程的自动入账。
- 客户与团队模块应完整呈现客户详情、KYC、银行资料、订单、成交、持仓、资金、归属和允许的人员管理操作；任何跨团队数据和操作继续由服务端隔离。
- 交易运营模块应完整呈现订单/成交详情、状态时间线、筛选、关联账户和现有允许操作；不得借后台完整性之名新增订单类型或改写交易状态。
- 内容、产品、客服、VIP、员工权限、验证器重置、审计、系统健康和部署状态模块，都必须列出可查看、可创建、可编辑、可发布、可撤销或只读的准确边界；没有业务授权的动作不显示也不可调用。
- 高风险操作使用明确危险样式、影响摘要、原因和二次确认；优先采用可恢复的停用/撤销，禁止用通用“删除”按钮处理资金、订单、KYC 和审计记录。
- 每个操作都必须处理 401/403、409 并发冲突、422 校验、429 限流、超时、未知结果和服务端失败；失败后保留用户输入，并提供刷新最新状态或安全重试路径。
- 后台首页与模块导航应显示角色真正可处理的待办数量和异常入口，但不得因为追求功能数量而扩大任何角色权限。

## 9. 安全与印度市场合规边界

- 延续员工 2FA、层级化验证器重置、会话撤销和角色隔离。
- 增加设备会话管理、异常登录告警、凭据轮换和最小权限服务账号。
- 生产密钥进入受控 Secrets Manager/KMS/Vault 类服务，仓库和镜像不得包含密钥。
- KYC 文件私有存储、病毒扫描、短时授权访问、字段脱敏和完整访问审计。
- PAN、Aadhaar、KRA/CKYC、SEBI/NSE/BSE 相关要求必须由持牌主体和法律/合规人员确认。
- 现有“无短信验证码注册”和“人工入金”保持不变，但在生产上线前必须形成正式合规差距清单；技术团队不得自行宣称合规。
- 外部 KYC、行情、客服和通知供应商统一通过 Adapter 接口接入，配置超时、熔断、重试和降级。

## 10. 可观测性与 SLO

以下为初始工程目标，不是未经压测的性能承诺：

- 市场时段核心 API 月可用性目标：99.95%。
- 普通读取 API：p95 小于 250 ms，p99 小于 800 ms。
- 已通过业务校验的订单接收：p95 小于 500 ms，不等同于成交时间。
- 行情断流检测：5 秒内；客户端展示过期状态：10 秒内。
- 关键资金事务重复执行成功次数必须为 0。
- 数据库恢复目标：RPO 不大于 5 分钟，RTO 不大于 30 分钟。
- 错误预算、告警阈值和容量基线按市场时段/非市场时段分别统计。

必须监控：

- 请求量、延迟、错误码、限流和依赖超时。
- 数据库连接、锁等待、慢查询、复制延迟和磁盘。
- Redis 连接、延迟、内存、淘汰和重连。
- Outbox 积压、消息延迟、重试、死信和重复消费。
- 订单接收、拒绝、撤单、成交、状态停滞和账本异常。
- 行情源连接、sequence 缺口、写入失败、WebSocket 客户数和重连风暴。
- KYC/文件扫描/客服/通知供应商健康。

## 11. 故障模拟矩阵

### 11.1 客户端与网络

- 2G/高延迟、间歇断网、DNS 失败、TLS 失败。
- 请求已到服务端但客户端超时。
- 用户连续点击、App 被杀、后台恢复、设备时间错误。
- WebSocket 反复断开、乱序、重复和缺包。

期望：不重复下单、不重复扣款；明确显示未知/处理中状态；恢复后主动查询最终结果。

### 11.2 API 与部署

- 单实例崩溃、滚动发布、版本不兼容、CPU/内存耗尽。
- 网关错误路由、限流误配置、请求体攻击。
- 旧客户端访问新 API，新客户端访问兼容 API。

期望：健康检查摘除故障实例；连接平滑迁移；契约测试阻止不兼容发布；可一键回滚。

### 11.3 PostgreSQL

- 连接池耗尽、慢查询、死锁、主库切换、只读副本延迟。
- 事务提交成功但响应丢失。
- 并发下单/撤单/结算争用同一账户或订单。
- 备份损坏和时间点恢复。

期望：事务原子；幂等重放返回首次结果；死锁有限重试；资金和订单不出现双写；恢复演练达到 RPO/RTO。

### 11.4 Redis

- Redis 完全不可用、主从切换、延迟飙升、键被淘汰。

期望：安全限流和会话撤销 fail closed；普通缓存可降级；不影响永久订单与资金事实；恢复后无重放漏洞。

### 11.5 消息与 Worker

- 消息重复、乱序、延迟、消费者崩溃、死信积压。
- 事务成功但消息未发；消息已消费但确认丢失。

期望：Outbox 最终投递；消费者幂等；顺序按 aggregateVersion 校验；死信可审计重放。

### 11.6 行情

- 供应商断流、旧报价、异常跳价、错误交易时段、Tick 洪峰。
- TimescaleDB 不可用或 K 线聚合延迟。

期望：标记 STALE/UNAVAILABLE；保留最后更新时间；交易规则按既有逻辑处理；历史图表失败不阻塞订单服务。

### 11.7 外部供应商

- KYC、文件扫描、客服、通知服务超时或返回 malformed payload。

期望：超时、熔断、有限重试；进入人工处理队列；不把供应商失败误报成业务成功。

### 11.8 安全

- JWT 重放、暴力登录、权限提升、越权 ID、恶意上传、日志注入、密钥轮换。

期望：会话撤销有效；服务端授权拒绝；文件隔离；日志脱敏；审计包含 requestId 但不含秘密。

## 12. 验证体系

- 单元测试：状态机、金额计算、权限、幂等和错误映射。
- 属性测试：金额守恒、重复事件、任意执行顺序和边界输入。
- PostgreSQL 集成测试：真实锁、并发事务、唯一约束和迁移升级。
- 契约测试：Flutter/Admin 与 API、供应商 Adapter、事件 Schema。
- E2E：注册、KYC、人工入金、下单、撤单、成交、提现和五角色后台。
- 负载测试：普通读取、行情 WebSocket、开盘突发、订单突发和后台报表。
- 长稳测试：至少覆盖完整市场时段及收盘任务。
- Chaos 测试：API、Redis、数据库、Worker、行情源和网络故障。
- 安全测试：SAST、依赖审计、Secret Scanning、DAST、上传和权限矩阵。
- 灾备演练：备份校验、时间点恢复、主库切换和应用回滚。

所有性能结论必须记录硬件、数据规模、脚本、持续时间、p50/p95/p99、错误率和瓶颈；不得只写“支持高并发”。

## 13. 交付阶段

### 阶段 0：基线与保护网

- 冻结业务契约，记录当前 API、数据库和 UI 状态。
- 建立真实容量基线、SLO、关键旅程和故障清单。
- 补齐资金/订单并发集成测试和生产数据规模查询计划。

### 阶段 1：客户端与后台失败状态

- 统一加载、空、错误、过期、离线、重试和重复提交状态。
- 完成 Groww/Zerodha/Upstox/Angel One 体验对照审计。
- 完成同一 Flutter 代码库的响应式 Web/PWA、安装/更新/离线安全策略和浏览器验收；不得复制交易逻辑。
- 不增加新金融产品，只优化已有流程。

### 阶段 2：入口与多实例

- 上线 WAF/网关策略、API 多实例、共享限流和会话撤销。
- 验证 WebSocket、多实例一致性和滚动发布。

### 阶段 3：数据可靠性

- PgBouncer、主库高可用、只读副本、备份验证和恢复演练。
- TimescaleDB 行情分离、K 线聚合和数据保留。

### 阶段 4：事件与后台任务

- 引入 Transactional Outbox、幂等 Worker、死信和重放工具。
- 通知、报表、导出、行情聚合逐步异步化。

### 阶段 5：交易与账本强化

- 集中状态机、状态版本、对账任务和异常隔离。
- 对撮合进行确定性回放与压测；没有证据不拆独立引擎。

### 阶段 6：全链路故障与容量验收

- 执行负载、长稳、Chaos、安全和灾备矩阵。
- 未达到门槛的阶段不得进入生产。

### 阶段 7：灰度上线

- 内部账号 → 小比例客户 → 分批放量 → 全量。
- 每批观察错误预算、账本对账、订单状态和客服反馈。
- 任一资金完整性异常立即停止放量并回滚。

## 14. 发布与回滚

- 每个阶段使用独立 PR、迁移脚本、验证证据和回滚说明。
- 数据库采用 expand/migrate/contract，禁止应用与迁移必须同一瞬间切换。
- 新基础设施先旁路/影子运行，再读取，最后才允许承担写流量。
- 所有新路径使用服务端 Feature Flag；资金核心逻辑不能仅靠客户端开关。
- 回滚不得回滚已经发生的资金事实，只回滚代码/流量并执行兼容恢复流程。

## 15. 最终验收

- 现有注册、登录、人工存款、交易和角色隔离回归全部通过。
- Android、响应式 Web 和可安装 PWA 使用相同业务契约；深链、刷新、安装、更新、离线和多标签页场景通过验收，离线金融写入为 0。
- 客户端与后台关键页面覆盖完整失败状态。
- 并发重试不产生重复订单、重复资金流水或重复审批。
- 主库、Redis、API 实例、Worker 和行情故障均有经过演练的处理路径。
- 最新主分支 CI、CodeQL、依赖审计和 Secret Scanning 通过。
- 灰度期间资金对账差异为 0，订单未知状态有可追踪闭环。
- 生产运行手册、告警责任人、升级/回滚步骤和灾备证据完整。

## 16. 留给实施计划决定的事项

- 结合实际部署供应商选择具体 WAF、网关、PostgreSQL HA 和消息总线产品。
- 根据生产硬件和真实峰值确定压测倍率与实例数量。
- 根据现有 UI 代码审计决定每个页面的组件拆分顺序。
- 根据法务/合规确认结果决定哪些印度证券合规适配器进入实施范围。
- 任何新增订单类型或金融产品必须另立产品设计，不属于本方案。

## 17. 审查后确定的工程决策

以下为不改变产品行为、但实施计划需要明确的工程决策：

- 不重建或改写历史资金流水。现有历史记录先做只读审计；新的可靠性约束采用兼容迁移。发现历史差异时进入人工核对清单，不自动改余额。
- 已向客户确认成功的订单和资金写入不得因单节点故障丢失。前述 5 分钟 RPO 只适用于可重建的报表、缓存和部分时序数据；核心金融数据采用同步故障域副本、持续 WAL 归档和事务后对账。
- Redis 不可用时，登录尝试限流、员工 2FA、会话撤销校验、密码恢复、订单提交、撤单、人工入金审批、提现审批和余额调整 fail closed；公开行情和普通只读内容可降级，但必须标注过期状态。
- 订单幂等键继续以账户 + clientOrderId 为核心作用域；人工资金与审批命令继续使用操作类型 + 业务对象 + 动作的稳定键。幂等结果与对应金融记录同寿命保留，不按短 TTL 删除。
- API 至少兼容当前生产客户端和前一个仍受支持版本；具体支持窗口通过现有 AppClientSetting 配置，在实施基线中记录，淘汰旧版本必须先提示升级。
- HNW 当前按单一运营主体、单租户设计；角色和客户归属是权限边界，不新增多租户模型。
- 99.95% 市场时段 SLO 覆盖登录、账户/持仓读取、行情状态、下单、撤单和订单查询；KYC、内容管理、报表和导出采用单独较低优先级 SLO。
- 数据库和应用升级默认要求滚动、混合版本兼容和无感切换；任何计划维护窗口必须单独获得用户批准。
- 生产主数据、备份、KYC 文件和日志优先部署在印度区域；最终地域、保存期限和跨境边界必须由实际运营主体和合规顾问确认。

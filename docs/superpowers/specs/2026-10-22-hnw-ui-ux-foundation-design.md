# HNW 全栈 UI/UX 基础升级设计

日期：2026-10-22
基线：`a1f624c`（`main`）
工作分支：`codex/ui-ux-foundation-2026-10-22`
首批范围：客户端 Home + Admin Dashboard

## 1. 目标

在不改变交易、注册登录和存款业务规则的前提下，建立一套可持续的 HNW 全栈升级路径：

1. 让客户端和后台使用一致、可验证的视觉语言。
2. 改善首屏信息层级、加载/错误/空数据反馈、响应式和可访问性。
3. 优化只读 API 和数据库查询，减少重复扫描与不必要的数据传输。
4. 把每次升级拆成可独立测试、回滚和合并的小提交。
5. 为后续 Markets、Portfolio、Profile、客户管理和资金运营页面建立共用基础。

## 2. 不可变业务契约

以下内容在本项目中视为冻结契约，首批及后续升级均不得改变，除非用户另行提出明确的业务变更：

- 交易撮合、下单、撤单、订单状态机、余额冻结/解冻、佣金和结算。
- 注册、登录、密码恢复、India 手机号校验、邀请码校验和现有认证响应契约。
- KYC 提交、审核规则和权限边界。
- 当前支持型存款方式、存款审核、上分流程和自助入金被拒绝的现有业务规则。
- 提现申请、审核、幂等键和资金流水写入规则。
- 客户端 Home · Markets · Trade · Portfolio · Profile 五个主导航入口。
- 现有金额精度、货币格式、敏感信息脱敏和审计要求。

实现约束：

- 首批客户端改造只修改展示层、状态编排和可访问性，不修改服务层请求、交易 payload 或资金写入。
- 首批后台改造只修改页面壳、视觉令牌、展示组件和只读数据编排。
- API/数据库优化只允许在读路径上进行；任何索引或查询改动都必须用测试数据和查询计划证明语义等价。
- 不把错误、权限拒绝或数据缺失静默转换成零金额、空订单或成功状态。

## 3. 现状与问题定位

现有仓库已经完成客户端 Home、Markets、Trade、Portfolio、Profile 的多轮展示层升级，并已有 Flutter 设计系统和后台共享运营组件。本设计不重复这些工作，而是补齐下一层基础。

已确认的结构性问题：

- Admin Dashboard 仍包含大量页面内联颜色、圆角和间距，难以保持像素级一致。
- `apps/admin/app/globals.css` 与 `apps/admin/app/app-content/page.tsx` 文件较大，通用壳和业务页面职责混杂。
- Admin Dashboard 当前由多个请求拼接数据；管理员概览 API 会读取账户及持仓后在应用层计算汇总，数据量增大后会产生不必要的扫描。
- 数据库已有较完整的基础索引，但尚未针对首批 Dashboard/列表查询形成可复现的 `EXPLAIN` 基线。
- 客户端已有 `AppColors`、`AppTypography`、`AppSpacing`、`AppRadius`、`AppCard`、`AppEmptyState` 和错误状态组件，下一步应将 Home 首屏所有新增视觉继续收敛到这些令牌。

## 4. 方案选择

采用“视觉基础 + 只读数据优化 + 分阶段页面升级”的方案，而不是一次性重写。

### 4.1 方案 A（采用）

先锁定契约和视觉基线，再以 Home 与 Dashboard 为垂直切片，最后扩展到其他页面。优点是用户能快速看到明显改善，同时能验证 API/数据库优化不会影响业务写入。

### 4.2 方案 B（不采用）

只做 UI 大改，暂不触碰 API/数据库。视觉反馈快，但会保留 Dashboard 查询扫描和数据状态不一致问题。

### 4.3 方案 C（不采用）

先做 API/数据库重构，再统一 UI。性能收益可能更早出现，但用户可见价值延后，且在没有页面基线时难以验证数据呈现是否完整。

## 5. 首批垂直切片

### 5.1 客户端 Home

目标是保持现有数据来源和资金入口不变，只提高信息层级与反馈质量：

- 继续保留总资产、收益、可用余额、保证金、未实现盈亏、指数、涨跌幅、新闻和公司展示。
- 快捷入口继续遵守现有存款/提现/交易路由；不新增或替换资金流程。
- 统一首屏卡片、标题、数字、状态标签、刷新按钮和错误重试样式。
- 加载态、空态、失败态和“数据更新时间”使用一致的状态模型。
- 窄屏下避免横向溢出；数字区域使用 tabular figures；收益不只依赖颜色表达。
- 保持现有 `formatPrice`、`formatSignedPrice`、`formatIndex` 和 API 字段语义。

预期触点：

- `apps/client/lib/pages/home_dashboard.dart`
- `apps/client/lib/widgets/home/` 下的现有 Home 组件
- `apps/client/lib/theme/` 下的现有令牌（仅在发现缺少语义令牌时增量补充）

### 5.2 Admin Dashboard

目标是把后台首页变成角色清晰、可扫描、可恢复的运营工作台：

- 保留现有角色隔离、菜单权限、资金提示和业务入口。
- 统一页面标题、更新时间、刷新、指标卡、快捷操作和风险提示的层级。
- 指标卡必须区分“数量、金额、风险、待办”，不能仅靠颜色区分。
- 失败时显示可重试错误状态；部分数据失败时不得伪造为零。
- 重要资金入口保持现有路径和操作说明，不改变上分、提现审核或交易管理动作。
- 移动端优先保证横向滚动、按钮触控尺寸和表格可读性。
- 将重复的颜色、圆角、阴影和卡片布局转移到共享运营令牌或共享组件。

预期触点：

- `apps/admin/app/dashboard/page.tsx`
- `apps/admin/app/globals.css`
- `apps/admin/components/OpsPageHeader.tsx`
- 现有 `OpsEmpty`、`OpsErrorState`、`OpsStatusTag`、`OpsToolbar` 等共享组件

## 6. 只读 API 设计

### 6.1 契约原则

- 现有客户端和后台正在使用的 endpoint、HTTP 方法、权限要求和字段含义保持不变。
- 若需要更高效的数据形状，优先增加内部 service/read-model 层；只有在确有必要时才增加向后兼容的新只读 endpoint。
- 金额在 API 边界继续使用明确的字符串或现有约定，禁止浮点替代 Decimal 语义。
- 所有聚合响应包含服务端生成时间或现有等价字段，便于 UI 展示“数据截至时间”。
- 错误继续遵守稳定 `code`、`requestId` 和权限/数据不可用语义。

### 6.2 Dashboard 读模型

第一步建立服务层的查询边界，而不是直接重写交易或账户写入服务：

1. 将用户数量、账户数量、订单数量、成交汇总和资产汇总定义为独立的只读查询。
2. 对持仓市值聚合使用经过 Decimal 校验的数据库聚合或受控批量查询，比较优化前后结果。
3. 对最近订单、成交和流水使用最小字段投影，继续脱敏客户信息。
4. 记录查询耗时、行数和失败原因，但不记录密码、token、完整手机号或银行信息。
5. 保留旧响应结构，先用契约测试证明等价，再切换实现。

### 6.3 缓存边界

仅考虑短时缓存非敏感、可重新读取的概览数据。余额、订单状态、存款/提现审核结果和任何资金写入结果不得依赖可能过期的缓存来做决策。

## 7. 数据库设计

数据库优化采用“先测量、后迁移”的顺序：

1. 为 Dashboard、最近活动、客户列表和内容列表建立固定查询样本。
2. 在本地 PostgreSQL 数据集上保存优化前的执行计划、耗时和返回行数。
3. 只针对高频过滤/排序组合增加可解释的普通或复合索引。
4. 索引迁移必须可重复执行，并附带 Prisma schema 与生成客户端检查。
5. 不改变资金、订单、交易、存款、提现表的字段语义、唯一约束或事务边界。
6. 用结果对比测试确认索引只影响执行计划，不改变返回数据。

候选读路径（需实施时重新以查询计划确认）：

- Dashboard 最近订单：`Order(placedAt)` 与现有账户/状态筛选组合。
- Dashboard 最近成交：`Trade(executedAt)` 与账户、标的投影。
- Dashboard 最近流水：`AccountTransaction(createdAt)` 与账户投影。
- 内容列表：现有模块、发布状态、生效时间和排序组合。
- 客户通知/设备/历史列表：沿用已有用户与时间索引，先检查是否已经足够。

## 8. 视觉系统与响应式规则

### 客户端

- 只使用现有语义颜色和设计令牌；新增颜色必须先成为语义令牌。
- 统一页面边距、卡片圆角、阴影、标题层级和数字字体。
- 支持至少 320 logical px、横屏、键盘弹出和 1.4 倍文字缩放。
- 重要信息同时使用文字、图标或状态标签表达，不以颜色作为唯一信息。
- 所有可操作图标保留至少 44dp 触控区域。

### Admin

- 继续使用 Ant Design 组件，但通过后台运营令牌统一颜色、圆角、边框和状态色。
- 页面内容区、标题区、工具栏、表格和详情抽屉采用固定间距阶梯。
- 保持角色色只表达运营上下文，不把角色色混用于资金成功/失败语义。
- 统一键盘焦点、`aria-label`、跳过导航、减少动画和 390px 以下布局。
- 表格在窄屏下允许横向滚动，但操作列和关键状态必须保持可见。

## 9. 测试策略

### 契约与业务保护

- 为注册/登录、存款路径、交易下单与撤单建立或补齐“响应和调用未改变”的回归断言。
- 对交易、资金和认证目录执行变更扫描，首批提交不得出现非必要修改。
- 对 Dashboard 聚合结果进行 Decimal 精度和字段等价测试。

### Flutter

- 先为新的可见状态或交互写失败测试，再实现。
- 运行格式化、`flutter analyze`、聚焦 Home 测试和全量测试。
- 为 320/360/412 宽度和大字体场景增加或复用 widget 测试。
- 若环境允许，增加 Home 关键状态的 golden/截图基线；无法截图时至少保留布局断言。

### Admin

- 运行现有 Node 测试、lint、TypeScript 检查和生产构建。
- 增加 Dashboard 角色、错误重试、部分数据缺失和响应式状态测试。
- 继续执行现有设计系统测试，确保角色菜单、权限和脱敏不回退。

### API/数据库

- 运行聚合 service/http 测试、构建和覆盖率门槛。
- 对迁移执行 Prisma 校验、空库部署和已有数据升级检查。
- 保存优化前后查询计划与结果对比证据。
- 继续运行本地 Docker 健康检查和认证/内容 smoke 测试；不执行真实资金操作。

## 10. 交付与回滚

按以下小步提交：

1. 设计与契约基线。
2. 客户端 Home 视觉与状态改造。
3. Admin Dashboard 视觉与共享令牌改造。
4. Dashboard 只读 API 查询边界与测试。
5. 数据库索引迁移（仅在执行计划证明有收益后）。
6. 集成验证、审查和 PR。

每一步都可单独回滚。任何测试发现交易、认证、存款、提现或 KYC 行为变化时，立即停止该步并回退，不通过 UI 变更掩盖业务差异。

## 11. 完成标准

本设计对应的首批实现只有在以下条件全部满足时才算完成：

- Home 与 Admin Dashboard 在目标断点下无横向溢出和明显布局跳动。
- 加载、空、错误、重试和更新时间状态可区分且不伪造业务数据。
- 交易、注册登录、KYC、存款和提现相关回归测试全部通过。
- API 只读优化前后结果等价，金额精度不变。
- 数据库迁移可重复、可回滚，查询计划有证据。
- Flutter、Admin、API、Docker smoke 和远端 CI 均通过。
- 变更保持在隔离分支，经过审查后再合并到 `main`。

## 12. 暂不纳入

- 更换交易供应商、行情供应商或撮合引擎。
- 更换注册/登录方式或存款通道。
- 新增自助入金、修改提现审核或引入新的资金审批角色。
- 重写整个 Flutter 状态管理、NestJS 模块或 Admin 路由体系。
- 没有视觉稿依据时凭空创建新的品牌颜色或大范围动效。
- 生产部署、真实账户操作和真实资金测试。

# HNW 总需求与企业级升级蓝图（中文总纲）

> 本文是产品、开发、测试、部署和验收共同遵守的上层需求基线，面向非技术负责人编写。
>
> 技术设计见 `docs/superpowers/specs/2026-10-25-hnw-india-stock-reliability-upgrade-design.md`；逐任务实施见 `docs/superpowers/plans/2026-10-25-hnw-enterprise-reliability-plan.md`。

## 1. 一句话目标

在不改变现有注册、登录、忘记密码、人工存款和核心交易方式的前提下，把 HNW 完善为成熟、稳定、安全、像素级精致、可长期维护、可验证、可部署、可监控、可恢复的印度股票 App、Web/PWA 和五角色后台管理系统。

“成熟”不等于承诺永不发生故障，而是做到：发布前尽量发现问题，故障发生时不轻易破坏资金和订单，影响可隔离，原因可定位，状态可恢复，发布可停止或回滚，后续维护不依赖某一个人。

## 2. 文档优先级与冲突处理

发生冲突时按以下顺序执行：

1. 用户明确确认的不可变业务规则。
2. 本总纲中的业务边界和验收标准。
3. 技术设计文档。
4. 实施计划。
5. 代码实现细节。

任何无法证明不影响受保护行为的修改都应暂停实施、记录风险并等待单独授权。

## 2A. 实施前环境与项目审计

- 执行环境是用户的 Windows 本地电脑，优先复用现有安全工作目录和已配置 Git。
- 开始修改前检查仓库路径、未提交修改、分支、标签、子模块、远程地址和基线 Commit SHA，不覆盖用户文件。
- 核对 Git/GitHub CLI、Node.js/npm、Flutter/Dart、Docker/Compose、PostgreSQL、Redis、PowerShell、Visual Studio/Build Tools、VS Code、Python 等实际需要的工具和版本。
- 不为了“全部安装”而引入无关工具；重大系统安装、系统配置、防火墙和公网端口变更需要单独授权。
- 审计目录架构、Flutter、Admin、API、配置、环境变量、数据库、第三方服务、定时任务、日志、异常恢复、依赖、测试、构建、部署和文档。
- 建立受保护代码地图，覆盖直接文件以及公共工具、数据库查询、时间、精度、异步机制和依赖等间接影响路径。
- 修改前记录构建、测试、API、数据库效果、注册、登录、恢复、存款、交易和关键截图基线，形成可重复的升级前后对比。
- 基线失败必须如实记录和归因，不得把原有失败隐藏为本次修复成功。

## 3. 绝对不能改变的客户业务

### 3.1 注册

- 印度手机号码 + 密码 + 邀请码/推荐码。
- 保留当前字段、校验、顺序、接口语义、邀请码归属和注册后流程。
- 不增加强制邮箱验证、注册短信验证码、Google/Apple/第三方登录。

### 3.2 登录

- 客户继续使用手机号码 + 密码登录。
- 保留当前会话、权限判断和接口兼容行为。

### 3.3 忘记密码

- 客户联系在线客服。
- 客服核实后签发恢复码。
- 客户使用恢复码完成密码恢复。
- 不改成短信、邮件或第三方自动找回。

### 3.4 人工存款

- 客户从存款/联系客服入口进入聊天。
- 客服提供所需信息，财务人员人工审核并入账。
- 不接入自动支付、银行卡自动扣款、UPI 自动充值、链上充值或任何绕过人工审核的方式。

### 3.5 交易

- 保留 BUY/SELL、MARKET/LIMIT、DAY/IOC/FOK、数量、限价、默认值、校验、确认和提交 payload。
- 保留资金/持仓冻结、撮合、撤单、成交、结算、手续费、状态和幂等语义。
- 保留交易策略、触发条件、行情解释、时间、精度和执行顺序。
- 交易请求超时后查询原订单状态，禁止盲目再次下单。
- 疑似核心交易缺陷只记录和说明，不在没有单独授权时直接修改。

### 3.6 交易页面

- 可以优化布局、视觉层级、文案、风险提示、错误提示和响应式体验。
- 不得改变字段、默认值、校验、确认含义、请求参数、提交接口和实际交易行为。

## 4. 明确禁止的内容

- 不增加加密货币、区块链、链上监听、智能合约、热冷钱包、TSS、多签或链上支付。
- 不擅自增加 F&O、杠杆、复制交易、篮子订单、GTT 或其他金融产品。
- 不为了技术先进而全面重写微服务、交易或认证系统。
- 不删除历史资金、订单、KYC、审批或审计数据。
- 不自动修改历史余额或持仓差异。
- 不使用真实资金、真实交易密钥或生产账户测试。
- 不把密码、Token、密钥、生产地址、私网地址或客户数据提交到仓库。
- 不强制推送、不重置 Git 历史、不覆盖用户未提交代码。

## 5. 印度股票产品定位

- 参考 Groww、Zerodha Kite、Upstox、Angel One 的信息层级、易用性、交易透明度和运营完整性。
- 不复制其商标、品牌、插画、源代码或受保护视觉资产。
- INR/₹、印度数字分组、IST、NSE/BSE、交易时段和节假日显示保持准确一致。
- 行情必须显示更新时间和质量；过期数据明确标注，不能伪装成实时数据。
- PAN、Aadhaar、KRA/CKYC、SEBI/NSE/BSE 相关内容由实际运营主体和法律/合规人员确认，技术团队不得自行宣称合规。

## 6. 客户 App 全量 UI/UX 升级

### 6.1 覆盖范围

- 一级页面：Home、Markets、Trade、Orders、Portfolio、Profile。
- 二级页面：股票搜索/详情、指数列表/详情、涨跌榜、市场新闻、通知、订单/成交/持仓详情、存款、提现、贷款、IPO、KYC、银行资料、账户设置、安全、语言、外观、法律/内容和客服。
- 流程页面：注册、登录、忘记密码、KYC 上传/自拍/签名/提交、订单确认和所有结果页。
- 覆盖层：抽屉、底部 Sheet、详情面板、筛选器、确认弹窗、公告、客服浮层以及成功/失败/警告对话框。

### 6.2 像素级标准

- 统一颜色、字体、字号、间距、圆角、阴影、图标、按钮、卡片和状态标签。
- 使用 8px 布局节奏和 44/48px 级别的可操作区域。
- 保持 AppBar、返回行为、标题层级、滚动、SafeArea 和键盘避让一致。
- 支持英语、印地语、1.0/1.4 字号、窄屏、横屏、平板、桌面和 reduced motion。
- 涨跌和状态不能只依靠红绿颜色表达。
- 不允许出现首页精致、进入二级页面后仍是旧式界面的断层。

### 6.3 状态展示系统

- 统一加载、提交中、等待审核、处理中、成功、拒绝、失败、空数据、离线、过期和未知结果。
- 共享状态组件包含语义图形、标题、说明、状态、更新时间、下一步、主次操作和可选时间线。
- 清理巨大沙漏、孤立 Spinner、默认素材和风格不一致的结果页。
- KYC 提交后显示“资料已收到”和 Submitted → Manual review → Result，不虚构审核时间。
- 明确区分网络加载、业务处理中、等待人工审核、结果未知和最终失败。
- 空状态说明为什么为空和用户能做什么；错误状态提供安全恢复动作。

### 6.4 客户端信息边界

客户 App/Web/PWA 不显示仓库、源代码、技术栈、内部 API、数据库字段、服务器/环境名、容器名、内部角色、供应商配置、堆栈、测试数据、密钥或内部 ID。

## 7. Web 与 PWA

- 使用同一 Flutter 客户端，不复制第二套交易逻辑。
- 支持手机、平板和桌面浏览器以及 Chrome、Edge、Safari、Firefox。
- 支持深链、刷新、前进/后退、多标签页、键盘和鼠标操作。
- 提供正式名称、图标、主题色、安装、更新、卸载、缓存清理和版本恢复。
- Service Worker 只缓存版本化静态资源和最小 App Shell。
- 登录、账户、资金、KYC、客服、订单、成交和行情接口不进入离线缓存。
- 离线时禁止下单、撤单、存款、提现和 KYC 提交，不排队、不恢复后自动重放。
- 多标签页同步退出登录和会话过期。
- 生产不公开 source map、秘密、私网地址或内部配置。

## 8. 后台员工认证

- 员工编号 + 密码保持不变。
- 首次登录强制绑定 Google Authenticator/兼容 TOTP。
- 后续使用密码 + 动态验证码。
- 验证器密钥加密保存，不写日志，不在绑定完成后重复明文展示。
- 管理员可重置其权限范围内业务员的验证器。
- 超级管理员可重置管理员的验证器。
- 重置后撤销旧会话并要求重新绑定，完整记录审计。

## 9. 五角色完整后台管理系统

### 9.1 角色隔离

- 超级管理员：治理、员工、权限、审计、系统健康和重大异常。
- 管理员：客户、KYC、业务员和客户归属。
- 财务：人工存款、提现、流水、差异和对账。
- 业务员：只访问自己的客户和被授权数据。
- 专用运营人员：只访问固定邀请码或被授权范围。
- 前端隐藏不代替服务端权限校验。

### 9.2 管理模块

- 客户、KYC、银行资料、归属、团队、邀请码。
- 存款、提现、流水、对账。
- 订单、成交、持仓和现有产品运营。
- IPO、OTC、VIP、公告、内容、行情配置和客服。
- 员工、角色、权限、2FA 重置和会话管理。
- 审计、系统健康、配置治理、部署和版本状态。

### 9.3 完整操作能力

每个模块建立“角色 × 数据范围 × 状态 × 操作”矩阵，并按业务需要支持列表、搜索、筛选、排序、分页、详情、关联记录、历史、创建、编辑、通过、拒绝、发布、撤销/停用、重置、导出或只读。

- KYC 待审核记录同时提供通过和拒绝；拒绝原因必填。
- 已审核 KYC 只读，不允许重复决定。
- 存款、提现等现有审批同时呈现通过、拒绝、原因、幂等结果和审计。
- 高风险操作显示当前值、目标值、影响、原因和二次确认。
- 资金、订单、KYC、审计不提供通用永久删除按钮。
- 每个操作处理 401/403、409、422、429、超时、未知结果和服务端失败。
- 失败后保留输入，支持刷新最新状态或安全重试。

### 9.4 长期维护

- 路由、菜单、标题、面包屑、权限和操作来自集中注册表。
- 使用统一分页页面、写操作契约、金额/状态/错误组件。
- 新页面和操作未登记时 CI 失败。
- 每个模块记录职责、API、权限、数据源、告警、故障和回滚方法。

## 10. API 与高并发可靠性

- 保持 NestJS 模块化单体，在真实容量证据不足时不盲目拆微服务。
- 完善输入校验、服务端授权、错误语义、requestId、幂等、超时、限流、熔断、健康检查和优雅关闭。
- API 至少兼容当前生产客户端和前一个仍支持版本。
- 多实例共享限流、会话撤销、任务租约和 WebSocket 状态。
- 外部供应商通过 Adapter 隔离，配置超时、有限重试、熔断和人工降级。
- 非权威副作用通过 Transactional Outbox 可靠投递，消费者必须幂等。

## 11. 订单、资金与数据库

- PostgreSQL 是账户、余额、冻结、持仓、订单、成交、审批、审计和幂等结果的权威事实源。
- Redis、缓存、消息、只读副本和时序库不能成为金融事实的唯一来源。
- 资金和订单写入必须在数据库事务中完成并使用合法状态机。
- 防止重复下单、重复撤单、重复结算、重复入金、重复提现审批和并发状态覆盖。
- 只重试明确可识别的数据库瞬时错误，并设置严格次数和抖动。
- 不重写历史资金流水；历史差异进入人工核对，不自动改余额。
- 数据库采用 expand/migrate/contract 兼容迁移。
- 完成连接池、慢查询、死锁、唯一约束、备份、WAL、时间点恢复和主库故障演练。

## 12. 财务对账

- 检查现金与流水、冻结现金与买单、冻结数量与卖单、成交与 Fill、幂等键、审批和结算。
- 后台支持查看、明细、确认、指派和处理说明。
- 不提供未经授权的自动修余额按钮。
- 上线和灰度期间核心对账差异目标为 0。

## 13. Redis、缓存、行情和 K 线

- Redis 用于限流、会话撤销、租约、协调和普通缓存，不保存唯一金融事实。
- Redis 故障时，员工 2FA、会话撤销、密码恢复、下单、撤单、入金/提现审批和余额调整安全关闭。
- 普通只读内容可降级，但必须标记过期。
- 行情处理重复、乱序、序列缺口、断线、重连、洪峰和过期。
- K 线/历史时序可使用 TimescaleDB 兼容存储，但故障不能阻塞订单服务。
- 不改变现有交易逻辑使用行情的方式。

## 14. 安全、隐私与数据治理

- Secrets Manager/KMS/Vault 类服务管理生产秘密；环境变量只引用，不在 UI 回显。
- 日志、指标、报错和分析数据脱敏，不记录密码、Token、TOTP 密钥和完整个人资料。
- KYC 文件私有存储、病毒扫描、短时授权、访问审计和最小权限。
- 防止越权、权限提升、JWT 重放、暴力登录、上传攻击、日志注入和供应链风险。
- 建立数据分类：公开、内部、机密、个人数据、金融数据和秘密。
- 建立保留和删除规则；法定金融/审计记录不得被普通删除请求破坏。
- 环境严格隔离：开发、测试、预发布、生产使用不同凭据、数据和权限。
- 定期执行 SAST、DAST、CodeQL、依赖审计、Secret Scanning 和权限复核。

## 15. 主动补充的成熟项目能力

以下是非技术负责人容易遗漏、但必须加入的内容：

### 15.1 时间、金额和数据质量

- 服务器统一保存明确时区的时间，客户显示 IST；禁止混用本地时间导致跨日错误。
- 金额使用定点 Decimal/最小货币单位，不使用浮点数处理金融事实。
- 所有报表标明数据截止时间、来源和是否延迟。
- 定期检测缺失、重复、负值、非法状态和关联断裂。

### 15.2 版本和兼容治理

- API、数据库、App、Web/PWA、Admin 和 Worker 都记录可追溯版本。
- 新版本先兼容旧结构，再切流量，最后清理旧结构。
- Feature Flag 只能控制新能力，不能只靠客户端开关保护资金逻辑。
- 明确旧客户端淘汰窗口并提前提示升级。

### 15.3 软件供应链

- 锁定依赖、审计 Dependabot、生成 SBOM、扫描镜像和校验构建来源。
- GitHub Actions 使用最小权限并固定可信 Action 版本。
- 发布产物绑定 Commit SHA、镜像摘要、配置版本和迁移版本。
- 每个依赖升级记录当前/目标版本、原因、破坏性变更、对交易/认证/API/数据库的影响、验证证据和回滚方式；无法充分证明兼容时保留旧版本。

### 15.4 客服与运营闭环

- 用户看到错误时获得可理解的说明和 requestId，而不是内部错误。
- 客服可按授权查询客户可见状态，但不能查看秘密或越权金融数据。
- 订单未知、KYC 驳回、入金/提现异常都有明确工单和升级路径。
- 高频问题形成标准回复和运行手册，但不能用模板掩盖真实失败。

### 15.5 所有权与变更管理

- 每个模块标明维护责任、审核人和告警负责人。
- 金融、权限、迁移和部署改动至少独立审查。
- 重大决策写入决策记录，避免人员更换后重复争论或误改。
- 过时功能先标记、迁移、观察，再移除，禁止突然删除。

### 15.6 成本与容量

- 记录数据库、Redis、对象存储、日志、CDN、行情和计算资源成本趋势。
- 扩容以真实 p95/p99、队列积压、连接数和市场开盘峰值为依据。
- 告警避免高基数和无限日志增长，设置合理保留期限。

## 16. 监控、告警与 SLO

- 覆盖 API、数据库、Redis、WebSocket、Worker、Outbox、行情、对账、登录/2FA、Web/PWA 和服务器资源。
- 市场时段关键旅程初始目标 99.95%，最终以压测和生产基线校准。
- 告警必须可行动，包含影响、检查、缓解、回滚、升级和禁止操作。
- 后台系统健康页只展示脱敏摘要，不提供服务器 Shell 或秘密。

## 17. 部署、服务器和灾备

- 提供统一 Windows/Linux 运维入口：预检、状态、日志、备份、部署、扩缩容、证书和回滚。
- 生产发布只从受保护 CI/CD 触发，使用最小权限、审批门和并发锁。
- 发布前验证配置、Secret 引用、证书、磁盘、时钟、镜像、备份、迁移和依赖健康。
- 采用灰度发布、健康检查、自动停止放量和安全回滚。

## 23. 给非技术负责人的词语解释

- **幂等**：同一个操作重复提交，不会重复扣钱、加钱或下单。
- **事务**：一组数据库操作要么全部成功，要么全部失败。
- **对账**：用不同记录相互核对，确认钱、持仓、订单和成交一致。
- **灰度发布**：先给少量用户使用，确认稳定后逐步扩大。
- **回滚**：新版本有问题时恢复旧代码或旧流量路径，不删除已发生业务。
- **SLO**：系统希望达到的可用性和性能目标。
- **RPO/RTO**：最多允许丢失多少可恢复数据，以及故障后多久恢复。
- **PWA**：可以从浏览器安装、看起来接近原生 App 的网页应用。
- **CI/CD**：每次代码改动自动执行检查、构建和受控发布。
- **SBOM**：项目所使用的软件依赖清单，便于发现供应链漏洞。

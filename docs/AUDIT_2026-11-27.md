## 新发现

### P1 密码恢复后台缺少客户归属约束

`apps/api/src/support/account-recovery.controller.ts` 的 StaffRecoveryController 注册在 SupportModule，允许 SUPPORT 和 ADMIN 访问。列表、消息读取、消息发送没有传递当前员工身份。`account-recovery.service.ts` 的 issue 方法使用手机号、CLIENT 角色和非 DISABLED 状态查询目标用户，没有核对 assignedBusinessId 或固定邀请码。

专用运营员可以列出普通客户的恢复会话，并为范围外客户签发重置码。恶意员工若自行发起目标手机号的恢复会话，即持有恢复 token，可结合签发的 code 执行重置。身份确认布尔值与外部会话编号均由调用者填写，不能提供客户归属授权。

修复应在所有员工恢复操作中校验当前员工身份，限定 SUPPORT 的固定邀请码及客户归属范围，并在签发事务内再次校验。增加普通客户、其他运营员客户和已转移客户的拒绝测试。

### P1 贷款还款存在丢失更新、重复登记和审计非原子问题

`apps/api/src/loans/loans.service.ts` 的 repay 方法在事务外读取 outstandingAmount，再计算并写回绝对金额，最后单独写审计。控制器和 DTO 没有还款业务流水号或幂等键。

两个请求同时读取欠款 1000，各登记 100，都会写入 900，实际应为 800。相同请求顺序重试也会再次扣减欠款。审计写入失败时，债务已经更新，调用方收到失败后重试可能进一步改变余额。

已用服务级并发夹具重现两次更新都写入 900，两个审计调用均发生。夹具保存在审计执行环境的 /tmp/hnw-audit-reproduction.spec.ts。修复应增加还款记录唯一标识，在事务内锁定贷款、验证余额并记录还款及审计，重试返回首次结果。

### P1 对账遗漏提现冻结资金

`apps/api/src/reconciliation/reconciliation.service.ts` 的 FROZEN_CASH_BUY_ORDERS 查询仅汇总未成交买单 frozenAmount。`withdrawal.service.ts` 的 createRequest 同样增加 accounts.frozenBalance。

正常账户提交 100 的待审核提现且没有买单时，对账会比较 frozenBalance=100 与 orderFrozen=0，产生错误差异。修复应分别汇总买单和待审提现冻结后求和，避免多表连接造成金额重复，并增加单独提现及混合冻结的 PostgreSQL 回归测试。

### P2 IPO 申购次数上限存在并发竞争

`apps/api/src/ipo/ipo.service.ts` 的 apply 方法先 count，再 create，两个操作没有共同事务锁。schema 和迁移未提供五次上限约束。

已有四次申购时，两个并发请求均读取四次并成功插入，最终达到六次。已用服务级并发夹具重现两个请求都被接受。修复应按账户与 IPO 锁定申购范围，在同一事务内检查并创建，同时明确请求重试的幂等语义。

### P2 撤销设备没有撤销设备会话

`apps/api/src/client-experience/client-experience.service.ts` 的 revokeDevice 只更新 userDevice.revokedAt。JWT 校验依据用户 authVersion，令牌没有设备会话标识，也没有查询设备撤销状态。refresh 与 biometricLogin 同样未关联该设备记录。

撤销设备后，原设备持有的有效令牌仍可继续使用。需要将设备撤销与会话撤销绑定，或明确采用撤销全部会话的产品语义，并验证访问令牌、刷新令牌和快捷登录凭据。

### P1 发布证据没有绑定实际部署版本

`.github/workflows/production-deploy.yml` 校验用户输入的 image_digest 格式，但调用 Coolify webhook 时没有传递 digest 或 commit。`scripts/post-deploy-smoke.mjs` 只检查健康和登录页的 HTTP 状态，没有校验 /health/version 的提交号。最终 evidence 把用户输入的 digest 写成发布镜像。

当 Coolify 指向不同提交或旧版本仍健康时，工作流可能成功并生成错误版本证据。修复应通过部署 API 明确指定提交或不可变镜像，并在冒烟测试中核验实际版本后生成证据。回滚工作流也需一起核查其版本绑定。
